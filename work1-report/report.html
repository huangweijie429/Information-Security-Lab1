3. 安全措施

风险实现方式
SQL 注入所有语句使用 ? 参数化查询（登录查询、q 过滤），不做字符串拼接； 用户名额外做白名单校验 ^[A-Za-z0-9_.-]+$
XSS返回前用 html.escape() 转义所有用户内容；回归测试断言 <b> 变成 &lt;b&gt;
认证失败bcrypt（cost 12）存口令哈希；HS256 JWT 带 exp/iss； 所有受保护端点经 HTTPBearer 依赖校验，缺失/伪造 token 返回 401

5. CVE-2018-12613 复现

目标：phpMyAdmin 4.8.1 本地文件包含（PMASA-2018-4，4.8.0/4.8.1 受影响，4.8.2 修复）。 环境按 Vulhub 同款配置构建（work1-cve/）：vulhub/phpmyadmin:4.8.1 + mysql:5.5， config.inc.php 用 config 认证，页面无需手工登录即可触发。

请求漏洞版 4.8.1修复版 5.2.2
GET /index.php?target=db_sql.php%253f/../../../../../../../../etc/passwd HTTP 200，页面中嵌入了 root:x:0:0:root:/root:/bin/bash 及整个 /etc/passwd HTTP 200，只返回 phpMyAdmin 页面，无文件内容
GET /（回归） 200，正常 UI 200，正常登录页（功能未破坏）

完整命令与输出见 work1-cve/evidence/01–04-*.txt。

6. 根因分析

index.php 会根据 target 参数包含一个文件：

if (! empty($_REQUEST['target']) && is_string($_REQUEST['target'])
    && ! preg_match('/^index/', $_REQUEST['target'])
    && ! in_array($_REQUEST['target'], $target_blacklist)
    && Core::checkPageValidity($_REQUEST['target'])) {
    include $_REQUEST['target'];
    exit;
}

Core::checkPageValidity() 用白名单校验参数，并在校验过程中又做了一次 URL 解码。 这正是缺陷所在：

  1. 请求携带 db_sql.php%253f/../../../../etc/passwd；
  2. 第一次解码把 %253f 变成 %3f，白名单只看 db_sql.php，校验通过；
  3. include 解析完整字符串时 %3f 变成 ?，后面的 ../ 逐级跳出 phpMyAdmin 目录。

一句话：被校验的值不是被使用的值——与 CVE-2021-41773 同属「解码/校验顺序」类缺陷，只是换成了 PHP。

影响不止读文件：config.inc.php 里就是数据库凭据；公开分析还把 PHP 写进 session （SELECT '<?=phpinfo()?>' 会存入会话）再包含 /var/lib/php/sessions/sess_<PHPSESSID>， 即可升级为命令执行。本环境的 access.log 是指向 /dev/stdout 的符号链接， 日志投毒变体不可用，因此只验证到文件读取这一步。

7. 修复与验证

层次改动为什么有效
补丁升级到 4.8.2（PMASA-2018-4）；本实验用仍在维护的 5.2.2 target 只在单次解码后校验，且必须命中真实页面白名单， db_sql.php%253f/../… 无法再通过
加固open_basedir 限制在 Web 根目录，allow_url_include=Off， 数据库账号最小权限 即便将来再出现包含缺陷，PHP 也读不到 Web 根之外的文件，也不能包含远程文件

修复后同一 PoC 只返回 phpMyAdmin 页面、无文件内容；首页/登录页仍正常（回归通过）。 poc.sh 可一条命令验证任意实例：漏洞版退出码 1，修复版 0。

8. 结论

「参数化查询 + 输出转义 + 强认证」能把自研代码的风险压得很低，却挡不住第三方组件自身的缺陷： phpMyAdmin 是运维日常工具，一个参数校验的顺序错误就能读出服务器上的任意文件。 这次 CVE 的教训有两层：依赖项要及时升级（消除已知缺陷），以及用最小权限兜底 （open_basedir、最小权限数据库账号），让「即使有漏洞」也读不到敏感文件。 两者叠加，回归测试才能同时证明「攻击失效」和「功能未坏」。
