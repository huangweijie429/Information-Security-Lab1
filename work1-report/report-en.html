1. Purpose

This work covers the full security lifecycle of an API: designing protection against the OWASP Top 10, wiring security tools into CI/CD, reproducing a real CVE in a controlled environment (the same configuration Vulhub uses), analysing its root cause, applying a fix and verifying both that the attack fails and that the application still works.

5. CVE-2018-12613 reproduction

Target: local file inclusion in phpMyAdmin 4.8.1 (PMASA-2018-4; 4.8.0 and 4.8.1 affected, fixed in 4.8.2). The environment in work1-cve/ mirrors the public Vulhub setup: vulhub/phpmyadmin:4.8.1 plus mysql:5.5, with config.inc.php in config auth mode so the page can be triggered without a manual login.

RequestVulnerable 4.8.1Fixed 5.2.2
GET /index.php?target=db_sql.php%253f/../../../../../../../../etc/passwd HTTP 200, the page embeds root:x:0:0:root:/root:/bin/bash and the rest of /etc/passwd HTTP 200, phpMyAdmin page only — no file content
GET / (regression) 200, normal UI 200, normal login page (functionality intact)

Full commands and outputs: work1-cve/evidence/01–04-*.txt.

6. Root cause

index.php includes a file chosen by the target request parameter:

if (! empty($_REQUEST['target']) && is_string($_REQUEST['target'])
    && ! preg_match('/^index/', $_REQUEST['target'])
    && ! in_array($_REQUEST['target'], $target_blacklist)
    && Core::checkPageValidity($_REQUEST['target'])) {
    include $_REQUEST['target'];
    exit;
}

Core::checkPageValidity() validates the value against a whitelist of pages and decodes it a second time while doing so. That double decoding is the flaw:

  1. the request carries db_sql.php%253f/../../../../etc/passwd;
  2. the first URL decode turns %253f into %3f, so the whitelist only sees db_sql.php and passes;
  3. include then resolves the whole string, where %3f is a ? and the ../ segments climb out of the phpMyAdmin directory.

In short: the value that is validated is not the value that is used — the same decode/validate ordering family as CVE-2021-41773, only in PHP instead of C.

The impact goes beyond reading files: config.inc.php holds database credentials, and public write-ups escalate to code execution by storing PHP in the session (SELECT '<?=phpinfo()?>') and then including /var/lib/php/sessions/sess_<PHPSESSID>. In this container access.log is a symlink to /dev/stdout, so the log-poisoning variant is unavailable and only the file-read step was verified here.

7. Fix and verification

LayerChangeWhy it works
Patchupgrade to 4.8.2 (PMASA-2018-4); this lab uses the maintained 5.2.2 target is validated after a single decode and must match a real page, so db_sql.php%253f/../… no longer passes the whitelist
Hardeningopen_basedir limited to the web root, allow_url_include=Off, least-privilege database account even with a future include bug, PHP cannot read outside the web root or fetch remote files

After the fix the same request returns the phpMyAdmin page with no file content, while the UI still works (regression passed). poc.sh verifies any instance in one command: exit code 1 for the vulnerable build, 0 for the fixed one.

8. Conclusion

Parameterized queries, output escaping and strong authentication push the risk in your own code very low, but they cannot stop defects in third-party components. phpMyAdmin is an everyday operations tool, and one ordering mistake in a parameter check is enough to read any file on the server. The lesson is twofold: keep dependencies patched, and add least privilege as a safety net (open_basedir, a minimal database account) so that "even with the bug" no sensitive file is reachable. Together they are what lets a regression test prove both "the attack fails" and "the feature still works".
